## Detailed Findings
### [High] Model-backed web endpoints and project creation have no per-user limits
- File: worker/index.ts:106-256
- Category: Security
- Description: `POST /projects`, `/projects/:id/plan`, `/summary`, `/summary/confirm` and `/answers` each trigger Gemini calls (`summarizeIdea`, `planQuestions`, `ensureDigest`) with no quota. Only run starts are capped (`DAILY_RUN_LIMIT`). The MCP path caps the same work with `spendModelCall` and `PROJECT_LIMIT` (worker/mcp.ts:95, :166), and the header comment in worker/service.ts:1 says limits should behave the same on both. Any signed-in user can loop these endpoints and burn the Gemini budget.
- Suggested Fix: Move the model-call and project-creation caps into worker/service.ts (reuse the atomic insert-select from `spendModelCall`) and apply them in the web routes too.

### [Medium] Deleting a project or user does not stop or purge its Durable Object run
- File: worker/index.ts:72-88, worker/index.ts:190-202, worker/run.ts:333-346
- Category: Correctness
- Description: Project and user deletion only touch D1 and R2. The `RunObject` keeps its alarm loop and its stored brief, drafts and log. A deleted project's run keeps calling Gemini until `commitDraft` fails on the foreign key, and the user's idea text and drafts stay in Durable Object storage after account deletion. The only stop signal is the browser sending `pause` over the WebSocket (src/screens/Construction.tsx:612), which does nothing if the tab is closed or the delete came from the webhook or another client.
- Suggested Fix: Add a `cancel()` RPC on `RunObject` that sets status to failed, clears the alarm and calls `storage.deleteAll()`. Call it for the active run on project delete and for every run on user delete.

### [Medium] `/answers` accepts any client-chosen questionId and inserts rows without bound
- File: worker/service.ts:49-61, worker/index.ts:243-255
- Category: Security
- Description: When the UPDATE matches nothing, `answerQuestion` inserts a new question row using the client-supplied id and prompt. The MCP route checks the id belongs to the project (worker/mcp.ts:282) but the web route does not. A client can add unlimited rows per project, and each call also triggers a model re-plan.
- Suggested Fix: Validate `questionId` against the project's existing questions in the web route, or cap the number of inserted orphan rows per project.

### [Medium] A failing attachment digest leaves the intake permanently stuck
- File: worker/intake.ts:115, worker/index.ts:233-241
- Category: Edge Case
- Description: `planQuestions` awaits `ensureDigest` outside any try/catch. `/summary/confirm` sets `summary_confirmed = 1` first and then plans, and `/plan` replans whenever there are no questions. If Gemini rejects an attachment (blocked, unsupported or oversized PDF or image), every confirm and plan call returns 502 and the project can only be deleted. `answerQuestion` already tolerates replan failures (worker/service.ts:65-70), but these two routes do not.
- Suggested Fix: Catch digest failures in `planQuestions` and continue with an empty context (as `summarizeIdea` does), or mark the digest failed so intake can proceed.

### [Medium] Daily run limit can be exceeded by parallel starts
- File: worker/service.ts:82-92, worker/service.ts:120-123
- Category: Edge Case
- Description: The daily count is read first, and the `run_starts` row is inserted several awaits later. Parallel `startRun` calls for different projects all see a count below the limit and all proceed. The per-project claim only prevents double starts of the same project. Each run can spend up to `RUN_TOKEN_BUDGET` tokens.
- Suggested Fix: Reserve the slot atomically with a conditional `INSERT ... SELECT ... WHERE (SELECT COUNT(*) ...) < limit`, as `spendModelCall` does, and fail with 429 if no row was inserted.

### [Medium] Raw Gemini error text is sent to the browser
- File: worker/run.ts:239-245, worker/run.ts:463
- Category: Security
- Description: A failed run stores `err.message.slice(0, 300)` in `state.error`, and failed critics log `err.message.slice(0, 160)`. Both are broadcast over the WebSocket. For `GeminiError` the message includes up to 500 characters of the provider's response body (worker/gemini.ts:108-109), so quota, project and key details can reach the client. The HTTP and MCP paths deliberately avoid this (worker/index.ts:41, worker/mcp.ts:70).
- Suggested Fix: Map `GeminiError` to a generic message in the run loop and log the detail server-side only.

### [Medium] Clerk session token is passed in the WebSocket URL and may be logged
- File: worker/auth.ts:58-60, src/lib/useRun.ts:30
- Category: Security
- Description: The WebSocket upgrade sends the session token as `?token=`. `wrangler.jsonc` enables Workers observability, which records request URLs, so tokens can end up in logs. Session tokens are short-lived but remain replayable until they expire.
- Suggested Fix: Authenticate with a one-time ticket from an authenticated HTTP call, or send the token in the `Sec-WebSocket-Protocol` header, and redact the query string in logs.

### [Medium] Live run view stops reconnecting if `getToken` fails
- File: src/lib/useRun.ts:26-27, src/lib/useRun.ts:49-53
- Category: Edge Case
- Description: `connect()` awaits `getToken()` with no error handling. `onclose` reschedules `connect` with `setTimeout`, so a rejected `getToken` (network blip, Clerk refresh failure) becomes an unhandled rejection and no further retry is scheduled. The UI stays on "Reconnecting…" while the run continues server-side.
- Suggested Fix: Wrap the token fetch in try/catch and, on failure, schedule the same backoff retry.

### [Medium] Unguarded `sessionStorage` access can blank the landing page
- File: src/screens/Describe.tsx:53, src/screens/Describe.tsx:70-71, src/screens/Describe.tsx:106, src/screens/Ready.tsx:13-16
- Category: Edge Case
- Description: `sessionStorage` is read inside a `useState` initializer and in effects with no try/catch. Browsers with site data blocked throw a `SecurityError` on access, which crashes `Describe` (the landing page) and `Ready` during render. `src/lib/theme.ts` already guards its storage use.
- Suggested Fix: Wrap the reads and writes in small try/catch helpers, as in `theme.ts`, and fall back to in-memory state.
